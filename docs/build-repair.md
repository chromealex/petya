# Исправление падающей сборки

Команды: «почини билд», «поправь падающую сборку APP-123», «пофикси билд кодексом». Явный исполнитель имеет приоритет; иначе используются существующие правила доступности Claude/Codex, лимитов и выбора проекта. При неизвестных лимитах или неоднозначном проекте Петя предлагает выбор через обычную панель агентов.

## Поиск материала

Сначала используется ключ задачи в команде, затем задача/тред текущей темы, приложенный лог, либо однозначное сохранённое обсуждение падения в Slack за последние сутки. Несколько задач/тредов требуют выбора кнопкой, номером или ключом. Для Jira учитываются разрешённые в настройках проекты. Существующая Jira-задача не создаётся заново; без Jira создаётся локальная запись поручения для ИИ.

Петя читает описание и комментарии Jira, текст Slack-треда и текстовые вложения .log/.txt/.out. До трёх файлов по 2 МБ из сервиса; контекст для исполнителя ограничен, длинные логи сокращаются вокруг ошибок. Ошибки чтения файлов сообщаются. Одного «build failed» недостаточно: нужен диагностический текст ошибки. Внешние сайты с логами, архивы и произвольные команды из сообщений автоматически не открываются и не исполняются.

## Запрос недостающего лога

В Jira создаётся комментарий с просьбой прислать лог, номер билда, ветку/коммит и команду сборки. Если найден комментарий о падении, упоминается его автор, иначе автор/создатель задачи. В Slack личное сообщение адресуется автору самого свежего человеческого сообщения о падении в выбранном треде. QA не назначается по умолчанию, люди между Jira и Slack по совпадению имени не сопоставляются.

После запроса Петя до суток проверяет ответ в задаче либо в треде своего личного сообщения Slack. Когда появится диагностический лог, автоматически подготавливает передачу ИИ. Если лог приложен непосредственно к следующей команде Пете, ожидание также продолжается с этим материалом. «Не запрашивай лог» запрещает внешнюю просьбу. «Отмени ожидание лога» отменяет ещё не переданное поручение; уже работающего исполнителя нужно остановить в его чате. «Статус исправления» показывает локальное состояние.

Состояние ожидания/отправки хранится зашифрованно и переживает перезапуск. Неоднозначный сетевой результат не повторяется автоматически. Смена подключения, выключенный модуль, очистка памяти или удаление записи по сроку останавливают продолжение от её имени. Полностью закрытое приложение не опрашивает сервисы. Несколько работ делят очередь с шагом не чаще минуты; ограничения сервиса могут задержать проверку.

## Передача и отчёт

Исполнитель получает контекст задачи, диагностические фрагменты и указание проверить репозиторий/ветку, воспроизвести ошибку, внести минимальное исправление и выполнить проверки. Логи объявляются недоверенными данными. Автоматические публикация изменений, деплой и переписка из чата исполнителя не запрашиваются. Петя использует существующий механизм отправки в чат без отдельного подтверждения.

При получении структурированного финального отчёта Петя может написать в исходную задачу/тред: что, по отчёту исполнителя, изменено, какие проверки проведены, либо чего не хватает. Отчёт отправляется, если Петя сам запрашивал лог или пользователь явно попросил отписаться. «Не отписывайся» запрещает публикацию. Успешное завершение чата не равно успешной сборке CI: независимая проверка CI прямо обозначена как неподтверждённая. Без структурированного результата Петя уведомляет пользователя и не придумывает исправление.

Автоматический статус текущая интеграция получает у Codex. Результат GUI-передачи в Claude автоматически недоступен; Петя уведомляет об этой границе и не публикует выдуманный результат. Если работа только по локальному файлу и адресат отчёта не задан, результат остаётся у пользователя. Для повторного исправления после завершения можно сказать «снова почини билд».

Нужны права чтения Jira и добавления комментариев; Slack требует чтения тредов, files:read, users:read, im:write и chat:write. Изменения OAuth-scopes находятся в исходниках OAuth-сервера; уже развёрнутый сервер необходимо отдельно обновить и переподключить Slack. Проверки используют имитации сервисов и исполнителя: реальные комментарии/сообщения/ИИ-поручения при тестировании не отправляются.
