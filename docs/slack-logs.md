# Analyzing Build Failures from Slack

«Петя, почему билд падает в этом логе?» (Petya, why is the build failing in this log?) looks for material in the last eight observed discussions in the Slack app. Observation works while the Slack module is enabled and Petya is running, every five seconds, only when Slack is the active app. macOS requires the «Универсальный доступ» (Accessibility) permission; Windows uses UI Automation. Observation does not work in browser-based Slack yet.

The Slack API does not report the history of opened threads. History from before Petya was launched is unavailable. The observer reads the text exposed to the accessibility tree after the Thread/Тред/Ветка/Обсуждение header, does not press buttons and does not scroll the window. If Slack does not expose the header or text, you need to open the thread/scroll to the error or attach the file manually. Virtualized and collapsed messages may be missing. Reading from the real Slack on both platforms requires additional verification; automated tests check snapshot processing, not the Slack interface.

The most recently viewed discussion with an error or a log is selected. Matching with the API context is done by an available link or by a single match of the full message/attachment name. For attached files without a link, Slack must first be refreshed (or its background refresh enabled). An ambiguous match is not selected automatically. Fresh replies are requested via conversations.replies; an incomplete page is reported. Without the API, only the visible text is available.

Text attachments .log/.txt/.out/.json/.xml/.yaml/.yml/.csv: no more than three of 2 MB each. A user token with files:read is required. The scope has been added to the OAuth server sources; an already deployed server does not update itself, so it will need to be updated and the account reconnected. External files and HTTP redirects are not downloaded; the Slack bearer is sent only to files.slack.com. Large logs are trimmed around error lines; the total context is limited to 60 000 characters.

The model is local Ollama only. The answer must name the error line, separate assumptions and suggest a check. Unavailability of the log is reported explicitly, not replaced with an invented cause. The answer and materials are saved as a separate topic and allow follow-up questions. A voice question is spoken using the existing dialogue mechanism. The thread link is shown when it could be determined. Snapshots and topics are stored encrypted according to the shared retention period of 1–7 days; «Очистить память» (Clear memory) deletes them.

Conversational prompts «Петя, посмотри эту фигню» (Petya, look at this thing), «глянь вот это» (take a look at this), «разбери эту штуку» (figure this thing out) also start an analysis. Priority: pending attachments → the active topic updated less than ten minutes ago → the last viewed Slack discussion no older than ten minutes. A general prompt does not require an error in the thread and does not force build diagnostics. If no fresh context is available, Petya asks to be shown the material. Such requests do not create tasks and do not launch executors.
